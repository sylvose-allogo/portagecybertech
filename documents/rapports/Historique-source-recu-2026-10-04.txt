Quel est le nom de ce design pattern de micro service ?

Le nom le plus juste, pour ce projet, c’est :
• Architecture micro services “Authorization Server + Resource Server”
• ou plus précisément : “OAuth2 / JWT-based micro service architecture”

Autrement dit :
•Un service est dédié à l’authentification et à la délivrance des JWT.
•un autre service protège les ressources et valide les tokens

Dans le vocabulaire micro services, on peut aussi dire :
•séparation par responsabilité (bounded contexts)
•architecture distribuée avec authentification décentralisée
•pattern “auth service + protected API service”

Ce n’est pas un pattern “micro service” ultra standard comme “Saga” ou “CQRS”, mais c’est bien un cas classique de micro services avec sécurité centralisée via OAuth2/JWT.

Il n’existe pas de “meilleure architecture” universelle en micro services : le bon choix dépend du besoin (performance, sécurité, cohérence, tolérance aux pannes, équipe, etc.).

Auth Service (Authorization Server) avec Resource Services (Resource Servers) et le protocole OAuth2/JWT

1. Les composants clés et leurs rôles

• Auth Service (Identity Provider / Authorization Server) :
• Gère l'authentification des utilisateurs (credentials, fédération OAuth2/OIDC tierce comme Google/Keycloak).
• Émet les jetons d'accès signés numériquement (JWT).
• Resource Service (API Micro service) :
• Héberge les données et les API métiers protégées.
• Valide localement le JWT sans solliciter l'Auth Service à chaque requête (grâce à la cryptographie asymétrique et aux clés publiques JWKS).
• JWT (JSON Web Token) :
• Jeton autoporteur contenant l'identité (sub), les rôles/permissions (claims) et une date d'expiration (exp).

2. Design Patterns principaux
A. Le Pattern Claim-Based Token (jeton riche en revendications)

• Fonctionnement : L'Auth Service intègre directement les rôles et permissions de l'utilisateur dans les claims du JWT.
• Bénéfice : Le Resource Service n'a pas besoin de faire d'appel réseau vers une base de données ou l'Auth Service pour savoir si l'utilisateur a le droit d'accéder à la ressource. L'évaluation de l'autorisation (RBAC/ABAC) est entièrement décentralisée et stateless.

B. Le pattern Decentralized Token Validation (validation cryptographique locale)

• Fonctionnement : L'Auth Service signe le JWT avec une clé privée (RSA/EdDSA). Les Resource Services téléchargent une seule fois (ou en cache via un endpoint /.well-known/jwks.json) la clé publique correspondante.
• Bénéfice : Chaque micro service de ressource valide la signature mathématique du jeton de manière autonome, éliminant les goulets d'étranglement.

C. Le pattern API Gateway/BFF (Backend For Frontend) pour le filtrage initial

• Fonctionnement : L'API Gateway intercepte les requêtes entrantes, valide l'existence et la structure globale du JWT à la périphérie (), puis route la requête vers le bon Resource Service en propageant le jeton.
• Bénéfice : isole-les micro services internes des requêtes non authentifiées.

D. Le pattern Token Propagation / Forwarding

• Fonctionnement : Si un Resource Service A doit appeler un Resource Service B pour accomplir une tâche, il transmet le JWT original d'origine dans l'en-tête HTTP (Authorization : Bearer <jwt>).
• Bénéfice : préserve le contexte de l'utilisateur tout au long de la chaîne d'appels interservices (traçabilité et audit).

3. Bonnes pratiques de sécurité

• Jetons à courte durée de vie (Short-lived tokens) : limitez l'expiration des Access Tokens à quelques minutes (ex. : 5 à 15 minutes) et utilisez des Refresh Tokens sécurisés pour renouveler les sessions.
• Algorithmes asymétriques : préférez la signature de type RS256 ou ES256 plutôt que HS256 (symétrique), pour éviter de partager un secret partagé (HMAC) sur l'ensemble de vos micro services.
• Défense en profondeur (Defense in Depth) : Combinez l'authentification utilisateur par JWT avec un chiffrement des transports interservices via mTLS (Mutual TLS) géré par un Service Mesh.
